## THE BUG THAT KILLED GPU1 — read this before converting any weight

`GRIMOIRE_W4A8=1` frees the MXFP4 payload of every converted weight. One
direct-payload site was left unrouted: the fused DN-qkv path, gated on
`bf_dn_qkv`, which is set by **`GRIMOIRE_BF16_DN_QKV` — Ornith sets it, Qwen
does not**. So Qwen never took that branch and Ornith did, dereferenced a
freed pointer at M=4096, and took 0000:35:00.0 off the PCI bus
(`forcewake register returns 0xFFFFFFFF`). No software reset recovers that;
it needs a power cycle.

Also fixed: `mlp_bf16`'s fallback checked `fmt != MXFP4`, but a converted
weight STILL reports fmt == MXFP4 -- only its payload is freed. The format
check is not a safety check. It now tests the pointer. Router guarded too.

**Rule: after any conversion change, `grep -n "\.w\.payload" src/grimoire.cpp`
and confirm every hit is either guarded or routed.**

## The 220 TG arithmetic — MTP alone cannot reach it

Decode 7.97 ms = MoE 2.25 + rest 5.72. In a verify batch the MoE part MUST
grow: 4 tokens route to ~22 distinct experts instead of 8 (that is what the
1.43x reuse means), so ~2.8x. Everything else is weight-bound and stays flat.

    verify(4) floor = 2.25*2.8 + 5.72 = 12.0 ms   (today 18.9)
    step  = 12.0 + draft 2.5 + snap/commit 0.9 = 15.4 ms
    / 2.37 committed = 6.50 ms/token = **154 TG CEILING**

220 TG needs 3.38 committed/step. Ornith MTP acceptance is 81.7 / 52.8 / 29.8
/ 12.2% -> 2.37. That gap is a DRAFTER problem, and **no DFlash or DSpark
drafter exists for Ornith** -- only `Qwen3.8-27B-DFlash2` and
`Qwen3.8-27B-DSpark`, both Qwen. So the EXPERIMENT doc's "DFlash V2 primary"
decision is a Qwen decision and does not transfer.

## The lever that DOES reach it: the MoE kernels are at 26-49% of roofline

- `moe_gate_up`: 8.4 MB / 28.33 us = **296 GB/s**
- `moe_down`:    4.2 MB / 26.88 us = **156 GB/s**
- roofline 602 GB/s

At roofline:

    decode 7.97 -> 6.6 ms                      = 151 TG baseline
    verify floor = 0.88*2.8 + 5.72 = 8.2 ms
    step = 11.6 ms / 2.37                      = 4.90 ms/token = **204 TG**

So the MoE kernel is worth ~25 TG on the baseline AND ~50 TG on MTP, and it
pays whether or not speculation is used. **This is the next work.**

## Most likely ROOT cause — NOT yet confirmed, do this first next time

The decode path is a single recorded **command graph** replayed per token

**separate unfused kernels with per-launch cost and no graph**. The +3.9 ms
is spread across four regions in proportion to their launch COUNT, which is
the signature of per-launch overhead, not per-region bandwidth.

**Next session: confirm this before touching any kernel.** Compare launch
counts decode vs verify (GRIMOIRE_TIMELINE marker count). If it is launch
overhead, the fix is to graph/fuse the verifier, NOT to tune individual

# PIPELINE-PARALLEL (multi-GPU) — 2026-08-27: infrastructure BUILT, blocked on USB4 device-1 allocation

## What is built and compiles (src/grimoire.cpp; backup src/grimoire.cpp.pre-pipeline)

Chose PIPELINE parallel over tensor-parallel: split LAYERS across the 2 B70s,
hand off the 8 KB hidden once per token (no per-layer all-reduce), so the slow
link is off the critical path and it achieves the capacity goal (FP8/BF16 that
does not fit one 32 GB card). `GRIMOIRE_PIPELINE=1`, default single-GPU unchanged.

- Both queues on ONE shared sycl context spanning both B70s (required; see below).
  q/q_aux rebuilt on the shared context at the TOP of build(), q1 = device-1 queue.
- `qL(i)` returns the queue owning layer i; `pipe_split = n_layers/2`.
- All ~273 per-layer allocations in the build loop routed to `qL(i)` so each
  card holds its half of the weights + per-layer KV/DN state.
- dev_copy / dev_copy_t stage through PINNED USM host + 64 MB chunks.

It splits correctly and LOADS 20 layers on GPU0, prints
"pipeline: layers [0,20) on GPU0, [20,40) on GPU1".

## The blocker — a USB4 hardware wall, thoroughly characterized

The first LARGE allocation/copy to device 1 (layer 20's `la_qkv`) throws
`UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY (error 39)`. Ruled out, by probes:

| test | result |
|---|---|
| bar/barprobe: alloc on each B70 alone | 39 GiB each — fine |
| bar2: 10 GB on device 0, THEN device 1 | device 1 gets 10 GB — fine |
| bar2 with 400 small allocs on device 0 | device 1 still fine — NOT an alloc-count limit |
| grimoire single-device context for q1 | fails |
| grimoire shared context {d0,d1} | fails |
| grimoire pinned USM host staging | fails |
| **grimoire vs bar2 — the one difference** | grimoire mmaps ~21 GB of model file; bar2 has NO mmap |

**Conclusion:** device-1 allocation over the USB4/Thunderbolt link fails once
the process holds grimoire's large (~21 GB) host mmap footprint. This is the
Thunderbolt IOMMU/BAR-window limit — the SAME hardware constraint behind the
"4x slower" TP and why vLLM needs multiprocess + CCL_TOPO_FABRIC_VERTEX_
CONNECTION_CHECK=0 + ZE_IPC_EXCHANGE=sockets (each rank = one process, one
device, no shared host-mmap pressure on the TB device). Both cards are
individually fine; it is the single-process COMBINATION over USB4.

## Three ways forward (for after OCuLink or now)

1. **OCuLink swap (days away):** proper PCIe Gen4 x4, full BAR/ReBAR. Very
   likely just works — retry `GRIMOIRE_PIPELINE=1` first thing.
2. **Reduce host mmap pressure now:** the loader mmaps the whole checkpoint
   (~21 GB VA). dev_copy_t already preads into a vector; try dropping/MADV_DONTNEED
   the mmap before loading device-1 layers, or load device-1 weights from a
   separate fd without a persistent mapping. Might unblock on USB4.
3. **Multiprocess (vLLM's model):** one GRIMOIRE process per B70, hidden-state
   handoff over a socket/shared-mem. Heaviest change; matches proven vLLM path.

## vLLM dual-GPU flags Ian uses (reference, in .pre-pipeline.NOTES)

# PIPELINE — DEFINITIVE: single-process is blocked on USB4; vLLM proves MULTIPROCESS is required

Read from the vLLM image: vllm/distributed/parallel_state.py — PP uses per-rank
send/recv, is_first_rank/is_last_rank; TP uses oneCCL all_reduce. BOTH are
MULTIPROCESS (spawn, one device per rank, ZE_AFFINITY_MASK per rank). vLLM never
does single-process multi-device. That is why it works on the USB4 link: each
process owns one device with its own IOMMU context; no shared cross-device host
memory pressure.

GRIMOIRE single-process pipeline (GRIMOIRE_PIPELINE=a,b, e.g. 24,16) is BUILT and
correct: shared context over both B70s, per-layer weight placement, pinned USM
host staging, MADV_DONTNEED at the boundary, configurable split matching
VLLM_PP_LAYER_PARTITION. It loads all GPU0 layers, then the first LARGE device-1
allocation throws error 39. Instrumented via GRIMOIRE_PIPE_DIAG=1: every dev_copy
(malloc_device + malloc_host + memcpy) SUCCEEDS on device 1; the throw is a DIRECT
malloc_device (MoE expert pack / KV cache). bar2.cpp proves that same 268 MB alloc
on device 1 works in ISOLATION (10 GB on each card, shared context). So it is the
process-global combination on USB4, not any single call. Tried and did NOT fix it:
separate vs shared context, pinned host staging, dropping the mmap resident pages,
different splits.

## Conclusion / next
Single-process multi-device does not work on this USB4 topology. Two paths:
1. OCuLink swap [days away]: proper PCIe Gen4 x4, full BAR. Retry GRIMOIRE_PIPELINE
   first; single-process may then just work.
2. MULTIPROCESS, vLLM's proven model: one GRIMOIRE process per B70, hidden state
   passed by send/recv [shared mem / socket]. Works on USB4 now, but a large
   runtime change. This is how vLLM does BOTH TP and PP.

The single-process pipeline code is preserved and reusable for OCuLink; it is gated
behind GRIMOIRE_PIPELINE and does not affect single-GPU runs.

## ORNITH TG OPTIMIZATION — ranked plan (2026-08-27, from 6 HF-link review)

Ornith baseline: 125.5 TG single-GPU (W4A8 + B70_MOE_SLOTS=4). 35B-A3B MoE
(3B active), 40 layers (30 GDN-linear + 10 full-attn), 256 experts top-8.
Decode engine at ~190 GB/s of 602 roofline (31%). MoE GEMV: gate_up 296,

### Six Ornith HF links reviewed — verdict
| link | useful for TG? | why |
|---|---|---|
| ultimatechris DFlash-SGLang | YES, BIG | block drafter, 6-8 committed/step, 2.32x (202->470) on 2xA100. THE lever. |
| EryriLabs BigBang-MTP | YES, QUICK | DENSE Qwen3.6 MTP head, 3.2-4.0 committed, +29% (131->169) on 3090. Reuses our Qwen dense-MTP code. |
| shisa-ai MTP-FP8 | head only, modest | same dense trained head; NO committed number; FP8 base is TG-NEGATIVE (2x bytes) and 36GB (needs TP2) |
| biMEMO int4-AutoRound-MTP | NO | headline "85-92%" is really 2.6 committed = same as our native head; int4 ~6% over MXFP4 (wash) |
| pyros oQ4e-fixed-mtp | NO | Mac/MLX affine mixed-precision quant, unsupported; same head as shisa; mixed-prec = TG-negative |
| gbuzhf GGUF-Abliterated-MTP | NO (runtime) | llama.cpp GGUF, not loadable; "96.77%" unverified/no committed; BUT its ICE error-travel bit-allocation idea = a separate real lever (below) |

Cross-cutting fact: NO off-the-shelf quant beats MXFP4 for TG (bandwidth-bound,
MXFP4=4.25 b/w is leanest). FP8/oQ4e/GGUF-mixed all move MORE bytes = slower.
And every MTP head tops ~2.6-4.0 committed (chained-draft decays with depth).
Only a BLOCK drafter (DFlash) reaches 6-8 committed.

### THE PLAN (ranked, do in this order)

**1. BigBang dense MTP head -- cheap quick win (~137-152 TG projected).**
   - Extract the ~19 BF16 dense MTP tensors from
     EryriLabs/Ornith-1.5-35B-A3B-BigBang-MTP (fc + 1 decoder layer + norms).
   - Load via GRIMOIRE's EXISTING Qwen dense-MTP path (already built+validated
     for Qwen: MtpHead struct, mtp_draft, embed/fc/decoder-layer). Do NOT use
     Ornith's native MoE-MTP machinery -- this head is DENSE.
   - Point it at our Ornith-1.5 MXFP4 target (same Qwen3.6 lineage -> compatible
     hidden states). VERIFY real acceptance/committed on OUR box first (their
     3.2-4.0 is code-biased; expect ~2.8-3.2 general).
   - Math: 3.2 committed, W4A8 verify ~19.5 ms + dense draft ~1.5 ms -> 21/3.2
     = 6.56 ms/tok = ~152 TG. Conservative 3.0/22ms = 137 TG. Both > 125.
   - GATED BY the verifier overhead (step 2) -- realized gain grows once verify
     is cheaper.

**2. Fix the verifier overhead -- the blocker for BOTH MTP and DFlash.**
   - Measured earlier: Ornith verify step ~2.4x a decode step (verify(1) ~= 
     decode(1) + 3.9 ms fixed overhead). Suspected: verifier runs unfused
     kernels with no command graph (decode replays one graph). Confirm by
     comparing launch counts decode vs verify (GRIMOIRE_TIMELINE marker count)
     BEFORE touching kernels -- do not rabbit-hole one region.
   - Fix = graph/fuse the verifier path so verify(1) ~= decode(1).

**3. DFlash block drafter -- the BIG win (~185-213 TG projected).**
   - ultimatechris/Ornith-1.5-35B-A3B-DFlash-SGLang: block_size 16, block-level
     (whole block one pass), 6-8 committed, 2.32x proven. Same DFlash2 family we
     studied+built the LOAD path for (Ornith DFlash2 struct exists in grimoire.cpp).
   - Remaining: drafter forward (sliding-attn layers + grouped conv + selector),
     block propose, block verify + rollback (GDN state snapshot 151 MB + attn
     pos rewind -- machinery from the MTP work is reusable). Verify batch uses
     the fast prefill/verify path from step 2.
   - Math: 7 committed, verify(16) ~30-38 ms + draft ~3 ms -> ~5.4 ms/tok =
     ~185 TG; verify(16) ~30 ms -> ~213 TG.
   - LARGE port but the ONLY thing that gives a >1.5x Ornith TG jump.

**4. MoE-bandwidth kernel work -- independent, compounds with all above.**
   - moe_gate_up 296 GB/s, moe_down 156 GB/s vs 602 roofline. down is at 156
     because rows are 512 nibbles=256 B (short-row latency). Needs a different
     decomposition (split I across sub-groups + reduce), not more rows
     (B70_MOE_DN_SLOTS=4 was a regression). ~2x on the BASELINE -> ~150 TG
     baseline, and every speculative number scales with it.

**5. (research) error-aware sub-4-bit** -- from the gbuzhf ICE idea: measure
   per-tensor output sensitivity on Ornith, drop tolerant tensors to 3-bit in a
   mixed MXFP4/int3 artifact -> fewer bytes = faster TG. ~10-20% if a meaningful
   fraction of the 3B active weights tolerate 3-bit. Speculative, our own work.

### Bottom line
Two things move Ornith TG: (a) DFlash block drafting [step 3], (b) the
MoE/verifier kernel work [steps 2,4]. Start with BigBang dense MTP [step 1] as
the cheap validation that speculation can win on our box, then the verifier
fix, then DFlash. MTP-quant repackages (links 3-6) bring nothing.
