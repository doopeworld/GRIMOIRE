## Native NVFP4: what the checkpoints actually hold (checked 11-04, no GPU)

My 11-02 note ("native NVFP4 dense kernels worth more than native FP8") needs a correction of scope:

| Checkpoint | NVFP4 tensors | Other tensors | What native NVFP4 would change |
|---|---|---|---|
| Qwen3.8-27B-NVFP4 (compressed-tensors, mixed) | MLP gate/up/down of layers 0-55 | FP8 per-channel: attention, linear-attention projections, lm_head, MLP of layers 56-63 | the 91.4% top-1 (held as INT8) / 83.2% (as MXFP4) could reach the file's own fidelity at 4.5 bits per MLP weight |
| Ornith-1.5-35B-A3B-NVFP4 (modelopt, mixed) | routed experts, shared experts, lm_head | FP8: linear-attention projections | today converted to MXFP4 at load |
| Qwen3.8-Flash-Next-NVFP4 (modelopt, mixed) | routed experts only (already native: tiered_moe.cpp, cpu_experts.cpp) | BF16 in the file: attention, shared experts, gates, HC; FP8: MTP experts, PLE table | nothing: `--proj bf16` already keeps its dense part exactly |

Plan when it is next: `--proj native` for safetensors, like GGUF: keep each tensor's file format. NVFP4 as a native block type in the
GGUF framework (`B70_NATIVE_GGUF`): llama.cpp's type 40 layout, 64 values in 36 bytes, four UE4M3 scales per 16 values, in each
16-value sub-block the low nibble of byte j is value j and the high nibble value j+8 (ggml-quants.c `dequantize_row_nvfp4`). GGUF has no
per-tensor scale, so the safetensors global scale becomes a per-row f32 factor applied to the output (merged gate/up keep one each).
Per-channel FP8 should map onto `--proj fp8` row scales without a second rounding; check whether the loader keeps the file's
bytes and scales or re-rounds. Measure: top-1 against the BF16 original
(`tools/bench/accuracy`) and decode speed against `--proj int8` on Qwen3.8-27B-NVFP4.
