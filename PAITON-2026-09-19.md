# Paiton-inspired recurrent replay for GRIMOIRE

This research branch implements compact native SYCL rollback for speculative
verification, explicit BF16/FP8 DFlash draft precision, and per-engine query
width. It starts at `3b9389d5b499202df3a02db1db4a0293edf6908c` on
`claude/new-session-pro26b`. It is separate from the Tower-ready branch.

**No B70 throughput result is claimed.** The implementation is opt-in and
retains the existing full-snapshot path for comparison. The CPU SYCL gates
verify arithmetic and integration; the Tower must establish real-model
correctness, XMX/AOT behavior, acceptance, memory use and speed.

## What was implemented

### Compact recurrent replay

With `GRIMOIRE_SPEC_REPLAY=1`, each local recurrent layer retains one
pre-verification FP32 checkpoint. During each ordinary production DeltaNet
step in a verification batch, it records, per value head:

```
normalized k[k_dim], decay a, correction[v_dim]
correction[v] = beta * (input_v[v] - a * dot(previous_state[v], k))
```

The correction is captured from the calculation already used to update the
state. Rollback replays only the accepted prefix using the same update:
`state[v,k] = fma(a, state[v,k], correction[v] * k[k])`. Each state element
is loaded and stored once across the whole replay. Dot products are not
recomputed and the model's `forward()` is not re-entered at old positions.
This preserves the original sequence of rounded updates.

The subgroup and row-wise kernels both record updates. The replay kernel
supports strided records for several layers, explicit event dependencies,
in-place checkpoint replay, zero accepted records, and widths up to 16.
Engine commits include the verified anchor, so their legal count is 1–16.
Invalid, stale and repeated recurrent commits are refused before mutation.
Reset, snapshot and restore invalidate the capture lifetime.

The existing convolution-history and hidden-state restore paths remain part
of the commit. Attention KV rows beyond the committed cursor are masked and
overwritten on subsequent steps, as in the original verifier. The normal
decode/prefill state lifecycle is still owned by GRIMOIRE; this does not
replace it with Paiton's request cache.

The memory saving is calculable. For 48 recurrent layers, 48 value heads,
128 key dimensions and 128 value dimensions, with capacity for 16 records:

| FP32 allocation | Full snapshots | Compact replay |
| --- | ---: | ---: |
| Pre-verify checkpoint | 144 MiB | 144 MiB |
| Per-step storage, 16 rows | 2,304 MiB | 36.14 MiB |
| Per-step storage saved | — | 2,267.86 MiB (2.21 GiB; 98.43%) |

This is a geometry calculation, not measured total VRAM. Conv/hidden buffers,
weights and attention caches are additional. Pipeline stages allocate only
their local layers. The banner prints actual local allocations at load.
The old per-token state-copy operations disappear on the compact path, but
the replay calculation itself costs work; only a card measurement can say
how much net decode time this saves.

The public
[Paiton adapter](https://github.com/Eliovp-BV/paiton-vllm-plugin/blob/8f56157c05eb6a53f6cdab00a115e47b42fed2d1/paiton_vllm_plugin/gdn_native_replay.py)
demonstrates the one-committed-block/compact-update design and the
accepted-prefix transition. Its native recurrence implementation is a
separately compiled HIP artifact, and its compiler is proprietary. This
change is an independent implementation using GRIMOIRE's existing SYCL
recurrence, not a claim to have ported that unavailable HIP source. No
vLLM, PyTorch or Python runtime dependency is added.

### DFlash settings and pipeline allocation

| Setting | Behavior |
| --- | --- |
| `GRIMOIRE_SPEC_REPLAY=1` | Use compact recurrent records; default remains full snapshots |
| `GRIMOIRE_DFLASH_DRAFT_FORMAT=fp8` | Quantize supported non-Muse draft projections to native FP8 E4M3 independently of the target |
| `GRIMOIRE_DFLASH_DRAFT_FORMAT=bf16` | Keep draft projections in BF16 for acceptance comparisons |
| `GRIMOIRE_DFLASH_M=8` | Eight query rows including the anchor, hence seven proposals |
| `GRIMOIRE_SPEC_STATS=1` | Existing per-request accepted-proposal statistics |

Draft width is resolved per engine at load. It was previously cached in a
process-wide static, as was the legacy BF16 switch; a second engine could
silently reuse the first engine's settings. Width now accepts only integers
2–16 and rejects malformed values. Without an override the old defaults
remain: 8 for an NInfer extracted head, otherwise 16. KV page size is a
separate setting. Query computation uses the chosen row count; allocation
capacity and hardware GEMM tile sizes can still be wider.

Without an explicit draft format, existing format selection remains in
place. Explicit FP8 conflicts with `GRIMOIRE_DFLASH_DRAFT_BF16` and is
refused for the Muse draft path. FP8 here uses GRIMOIRE's quantizer; loading
a checkpoint with “FP8” in its name is not proof of identical Paiton draft
numerics or acceptance.

An additional bug was found in the original allocation predicate: early
pipeline stages allocated rollback buffers for an MTP request but not for
a DFlash-only request. They have no local DFlash head, yet still own
recurrent state that must roll back. A configured DFlash request now
allocates the buffers on every pipeline stage, for both storage modes.

## Verification

Rebuilt and executed on 2026-09-19 with Intel DPC++ 2026.1.1,
`spir64`, `GRIMOIRE_NATIVE_ONLY`, per-kernel device images and Intel's
OpenCL CPU runtime on an AMD EPYC 9V74. This is native SYCL execution on
a CPU, not an AMD GPU benchmark.

| Check | Result |
| --- | --- |
| Native CLI and server | Compiled and linked |
| `make test test-correctness` | All host suites passed, including new runtime-setting checks |
| Replay kernel, subgroup mapping | 180 accepted-prefix cases, zero failures |
| Replay kernel, `B70_DN_STEP=0` | 180 accepted-prefix cases, zero failures |
| Engine, `--single-process` | 16 BF16/FP8 rollback rounds; recurrent/conv/hidden state and next tokens identical |
| DFlash2 fixture | Live selector, independent widths 4/8 and BF16/FP8 draft formats; actual proposals executed |
| K2 kernel and engine gates | Both passed, zero failures |
| Negative control: replace replay decay with 1 | Failed as expected: 310 failures across 180 prefixes |
| Two-stage PP and existing TP/PP speculation gate | Blocked locally: Unix `socket()` returns EPERM before ranks connect |

The replay gate warms state for 41 tokens, tests widths 1/2/4/8/16 at
every prefix, poisons rejected records with NaNs, checks interleaved-layer
stride guards, compares recording versus ordinary production recurrence,
checks in-place replay and decodes after rollback. Engine checks also
refuse invalid, stale and repeated commits without changing state.

The full `test_spec_e2e` suite is **not claimed green here**: its socket
tests cannot run in this workspace. The new pipeline gate is compiled and
its stage allocations were reached, but cross-stage execution still needs
a host with Unix sockets. The default Paiton gate and Tower preflight
continue to require that check; no production guard was weakened.

The new tests are `tests/test_dflash_runtime.cpp`,
`tools/test_deltanet_replay.cpp` and `tools/test_paiton_e2e.cpp`.
`make test-paiton` runs the host setting checks, both recurrence mappings,
and the engine gate. They are also integrated into `build_b70.sh` and
`tools/preflight_b70.sh` so the Tower can run the same gates.

To reproduce off-card, install the real toolchain documented in
`TOOLCHAIN-IN-A-CONTAINER.md`, then run:

```bash
make -j3 test test-correctness
make -j3 native test-paiton SYCL_TARGET=spir64 \
  NATIVE_FLAGS='-fsycl -fsycl-targets=spir64 -O2 -std=c++20 -fno-fast-math -ffp-contract=fast -fno-math-errno -fsycl-device-code-split=per_kernel -Wmisleading-indentation -DGRIMOIRE_NATIVE_ONLY -Iinclude -Isrc'
```

If the host explicitly prohibits Unix sockets, build the two native gate
binaries with the same flags, run `test_deltanet_replay` in both modes,
and run `test_paiton_e2e --single-process`. That mode prints the PP skip
and does not establish pipeline parity. Run the default gate on the Tower.

On a CPU device the engine gate explicitly calls the existing no-XMX
batched verification path. The production CPU hybrid-speculation refusal
is retained. The new gate does not pretend a CPU has XMX hardware.

## B70 acceptance and performance gate

1. Fetch this research branch on the Tower. Run
   `tools/preflight_b70.sh /models/<target-directory>` first, including
   the real-model text check. Follow `DAY-ONE.md` for the native image;
   preserve the bridge-first build order if using the bridge profile.
2. Compare full snapshots with compact replay on the same real checkpoint,
   projection format, prompt, draft precision, query width and generation
   budget. Keep prefix reuse and concurrent speculative serving out of
   this comparison because those combinations remain refused.
3. Read the generated text and require greedy token parity. Then measure
   decode throughput, TTFT, prompt throughput, peak VRAM and accepted
   proposals per verification step. Repeat across prompts and context
   depths; keep cold loads and compilation out of steady-state timings.
4. Compare BF16 versus FP8 draft precision separately. Next compare query
   widths 4, 8 and 16. Seven proposals are a starting hypothesis, not a
   proven B70 optimum.
5. Repeat on two B70s through `tools/pp2run.sh`, measuring OCuLink boundary
   traffic and DFlash tap traffic. The two-process gate compares stage-local
   state restoration; it cannot establish PCIe behavior or throughput.

Example single-card A/B using the repository's safe runner (replace the
two model paths and projection format with the validated Tower recipe):

```bash
for replay in 0 1; do
  EXTRA_ENV="GRIMOIRE_DFLASH_MODEL=/models/<draft-directory>
GRIMOIRE_DFLASH_M=8
GRIMOIRE_DFLASH_DRAFT_FORMAT=fp8
GRIMOIRE_SPEC_REPLAY=$replay
GRIMOIRE_SPEC_STATS=1" \
  GPU=gpu0 LIM=600 bash tools/tune.sh "paiton-replay-$replay" \
    /grimoire/bin/grimoire -m /models/<target-directory> --proj mxfp4 \
    -p 'Explain why the sky looks blue, using clear physical reasoning.' -n 256
done
```

`tools/tune.sh` uses the Tower's configured image. For a native-only image,
set `GRIM_IMAGE` to the image built and verified through `DAY-ONE.md`.
Never wrap a bare GPU `docker run` with host `timeout` (CLAUDE.md rule 6).

## Remaining work, ordered by evidence

- **FP8 KV already exists** in GRIMOIRE's attention paths. Measure its
  actual memory/accuracy tradeoff; do not implement a duplicate cache.
- **Continuous batching already exists** at this base. The older serial
  server statement in `PERF-2026-09-17.md` is superseded by
  `CONCURRENCY-2026-09-17.md`. Combining speculative drafts with concurrent
  requests still needs per-request replay state and scheduler integration.
- **Prefix caching plus speculation remains refused.** Paiton's compact
  adapter likewise requires prefix caching off and selects another GDN
  path for the chat profile. Supporting both requires explicit cache and
  recurrent-state ownership work, not removal of a guard.
- **4096-token prefill chunks are a measurement candidate.** The old AMD
  profile used that size; the current chat profile differs. This patch
  does not invent a GRIMOIRE chunk-size switch or change prefill tiling.
- **GDN projection fusion is not enabled.** GRIMOIRE's existing B70
  measurement found its merged projection slower. Revisit only with
  matching card measurements and a concrete dispatch/layout hypothesis.
- **W4A8 versus MXFP4 needs B70 measurements.** Preserve freed-payload
  checks, N-multiple-of-256 guards and the small-M tile rules. R9700 HIP
  kernel choices cannot establish the best Intel XMX configuration.
- **Hybrid TP speculation stays refused.** This change does not add the
  missing TP batched verifier. It does not claim full-model, AOT, XMX,
  OCuLink, long-context or real-checkpoint validation off the card.
