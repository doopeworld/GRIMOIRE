# Qwen4-Exp / Qwen3.8-Flash-Next in GRIMOIRE

Status as of 2026-09-16. Read this before touching `qwen4_exp` anything.

`huggingface.co` is blocked by the work container's egress proxy, but
**github.com is not**, so the vLLM implementation was cloned and the
relevant modules extracted into `ref/qwen4_exp_*.py`. Nothing here was
inferred from the model card; every claim below cites the reference.

## What this model is

`model_type: "qwen4_exp"` (wrapper) / `"qwen4_exp_text"` (text tower).
125B total, ~6B active, plus a ~51B n-gram embedding table.

**`Qwen4ExpTextConfig` INHERITS `Qwen3NextConfig`**
(`ref/qwen4_exp_config.py:34`). That is the single most useful fact in
this file: the body is a Gated-DeltaNet + MoE hybrid, which is the shape
GRIMOIRE already runs for Ornith and Qwen3.5.

Published layout: 48 layers as 12 x (3 x GDN + 1 x QSA), hidden 2560,
MoE 512 experts + 1 shared, QSA at head_dim 256 over 24 heads, GDN at
head_dim 128 over 16 QK / 48 V heads.

Three mechanisms sit on top of that base, and **each is fluent when
faked** -- that is why the engine refuses by name rather than running the
part it recognises.

## 1. HyperConnections -- DONE (kernels)

`ref/qwen4_exp_common_hyperconnection.py`. The residual stream is
`hc_count` (4) STREAMS wide: `[hc*hidden]`, not `[hidden]`.

    mix:      normed = grouped_rmsnorm(hyper)        per stream
              g = silu(W_down @ normed / hc)         [lowrank=320]
              g = sigmoid(W_up @ g)                  [hc*hidden]
              block_in[h] = mean_c( g[c][h] * normed[c][h] )

    combine:  inj[c] = 2 * sigmoid((W_inj @ normed)[c] / hc)
              out[c][h] = hyper[c][h] + block_out[h] * inj[c]

Traps, all pinned in `bin/test_k2_kernels`:

- **The norm is `(1 + w)`, NOT `w`.** The class is called
  `GroupedGemmaRMSNorm` and gemma-4 is the one architecture here that
  applies its weight directly -- but this one is
  `normalized * (1.0 + self.weight)` with the weight initialised to
  ZEROS (`ref:87`). Rule 11, pointing the opposite way to the name.
- It is **grouped**: each hidden-wide stream normalises on its own
  variance.
- `combine` adds to the **UNNORMALISED** stream.
- The `/hc_count` is **inside** `silu` and `sigmoid`, not outside.

Kernels: `launch_hc_norm`, `launch_hc_gated_mean`, `launch_hc_combine`.
The two projections are ordinary matmuls and use the existing GEMV.

## 2. QSA -- DONE (kernels)

Reference math is in vLLM's own test,
`tests/models/qwen4_exp/test_qsa_reference.py` (the shipped path is CUDA,
the test is plain torch). Copied to `ref/qwen4_exp_nvidia_qsa.py` and
`ref/qwen4_exp_nvidia_indexer_qsa.py`.

    1. INDEX   logits = relu(einsum("rhd,rnd->rnh", q, keys)).sum(-1)/sqrt(d)
    2. SELECT  top indexer_budget/compress_ratio blocks, visible range only
    3. EXPAND  block b -> tokens [b*ratio, b*ratio+ratio), cut to budget,
               masked to < seq_len; holes stay -1
    4. ATTEND  ordinary flash math over the GATHERED LIST

Traps, pinned:

- **`relu` per head, THEN summed**, then scaled. Sum-then-relu is the
  natural misreading and produces a different RANKING -- so it selects
  different blocks, and attention over the wrong 2048 tokens is still
  fluent. The A/B puts the two 0.92 apart.
- **A `-1` index is a hole.** Clamping it to token 0 makes a short
  sequence attend to its first token repeatedly and still softmax to
  something plausible.
- Config rules (`_validate_qsa_config`): `indexer_kv_heads` must be 1,
  `indexer_budget / indexer_compress_ratio` must be 512 or 2048.

Kernels: `launch_qsa_index_logits`, `launch_qsa_expand_blocks` (ops.cpp),
`launch_qsa_attention` (attention.cpp, templated on accumulator width
like every other flash kernel here).

## 3. PLE n-gram embedding -- DONE (kernels)

`vllm/models/qwen4_exp/nvidia/ops/ple.py`, whose docstring is the spec.

    ids:  offset[h] + (xor_i(token[t-i] * multiplier[i]) % size[h])
    gate: d = dot(RMSNorm(key), RMSNorm(query)) / sqrt(H)
          g = sigmoid(sign(d) * sqrt(max(|d|, 1e-6)))
    conv: silu(sum_k weight[k] * history[t + k*dilation]) added to the
          gated output  -- the engine's causal conv1d already does this

**THE TABLE LIVES IN HOST MEMORY.** 20,000,000 rows, and vLLM pins it
(`Qwen4ExpPLEPinnedHostEmbedding`) rather than putting it in VRAM. It is
a sparse gather -- only the rows for the current tokens are read. This is
the architecture's intended design, and it is what makes a 125B + 51B
model tractable on a box that cannot hold that table in VRAM. GRIMOIRE is
otherwise VRAM-only; plan this one table as the exception.

Traps, pinned:

- **Each head has its own n-gram ORDER**: head h covers
  `h/heads_per_ngram + 2`, so the first block of heads are BIGRAMS and the
  next TRIGRAMS, and a predecessor enters a head's xor only while
  `shift < order`. Mixing every predecessor into every head collapses the
  orders and still yields valid table indices.
- **The EOS boundary is STICKY**: walking backwards, once a predecessor is
  EOS every older one is EOS too. That is what stops an n-gram spanning
  two documents, and reading through it is invisible in any
  single-document test.

Kernels: `launch_ple_ngram_ids`, `launch_ple_gate`.

## What is LEFT: the forward path

All three mechanisms exist as verified kernels. Nothing dispatches them,
and `Grimoire::unsupported_reason()` still refuses `qwen4_exp` by name.
That is deliberate: two of three would be fluent and wrong.

The remaining work, with the reference lines that define it
(`ref/qwen4_exp_nvidia_model.py`):

1. **Multi-stream state.** `forward()` starts with
   `hidden_states = embed(ids).repeat(1, hc_count)` (`ref:510`) -- the
   embedding is REPEATED, not projected. Every per-layer buffer that
   holds the residual becomes `hc_count * hidden` wide.

2. **Deferred combine.** The decoder layer returns
   `(hidden_states, block_output, injection)` and the NEXT layer's
   `combine_and_mix` consumes the pending pair (`ref:276-332`). It is not
   a per-layer `combine` immediately followed by a `mix`; fusing them is
   the reference's own shape and the buffers follow from it.

3. **PLE placement.** A layer with `ple` materialises any pending combine
   FIRST, because PLE adds directly to the multi-stream state
   (`ref:290-296`). `ple_layer_ids` is **1-BASED** in the config
   (`ref/qwen4_exp_config.py:127`) -- it is stored verbatim in
   `cfg.ple_layer_ids` and must be converted at the point of use, not at
   parse time.

4. **Layer dispatch.** `linear_attention` -> the existing DeltaNet path;
   `qwen_sparse_attention` -> QSA. `cfg.qsa_attention[i]` already records
   which is which, per layer.

5. **The tail.** A final `hyper_connection_mixer` consumes the last
   pending combine and produces the single stream the head reads
   (`ref:576`).

6. **PP.** A stage boundary transports ONE tensor, so a pending combine
   must be materialised before sending (`ref:568-574`). Getting this
   wrong desynchronises the stages rather than producing a wrong number.

7. **The upload path and a `mini::qwen4_exp()` fixture**, so it becomes a
   row in `bin/test_model_matrix` the same day the forward path lands
   (rule 14).

Until all of that exists, the refusal stays. A model with two of three
mechanisms produces fluent text that is not the model's output, which is
the failure mode this whole file is organised around.
