# Where GRIMOIRE's speed actually is, and what to do about it

Written 2026-09-17, off the card, after reading GGZ14/vllm-mxfp4 -- an
AMD RDNA4 stack serving the same model family (Qwen3.8-27B) with the
same techniques (MXFP4 W4A8, gated DeltaNet, MTP/DFlash drafting).  It
is the closest thing to a comparable this project has.

**Nothing here is a timing.** No B70 was involved.  Two of the three
findings are counts or facts about the code, which are machine
independent; the third is explicitly a question for the card.  Rule 8
stands: none of this is a benchmark.

## 1. The server is SERIAL.  For agent workloads this is the whole story.

`tools/grimoire_server.cpp` says so in its own header and means it:

    requests are served one at a time behind a mutex -- a second request
    queues rather than corrupting the first's state

So with eight agents connected, seven are waiting.  Aggregate
throughput equals single-stream throughput, and per-agent latency is
eight times worse than it looks.

This matters because it disarms most of what the AMD stack gained.
Their headline decode wins are at a BATCH:

| their change | 1 stream | 4 concurrent | 8 concurrent |
|---|--:|--:|--:|
| small-M decode GEMM (split-K) | -8.3% | **+28.5%** | +19.7% |
| dynamic verify width | a wash | -- | **+11-13%** |
| decode band extended to M<=128 | -- | -- | +30% at 16 |

Every one of those needs several sequences in flight.  GRIMOIRE never
has more than one, so porting the split-K decode band today would buy
approximately nothing.  **Continuous batching is the prerequisite, and
it is a feature, not a tuning knob**: a KV cache that can hold several
sequences at once, a scheduler that admits and evicts them, and a decode
step that runs M rows where it now runs one.  The batched-prefill
machinery (`prefill_gemma4`, `prefill_qwen4_exp`, the m16 tiles) is the
half of it that already exists.

If agent workloads are the target, this is the top performance item and
nothing else on this page comes close.

## 2. Launch count: ~29 per layer per decode token.

Measured off-card with `tools/count_launches.sh`, which counts
`urEnqueueKernelLaunch` at two generation lengths and subtracts so load
and prefill cancel.  On the 4-layer dense fixture:

    launches at n=1  : 906
    launches at n=11 : 2066
    per decode token : 116          (~29 per layer)

Extrapolated to a 48-layer model that is ~1400 per step, which is
almost exactly where the AMD stack STARTED (1477) before it spent real
effort getting to ~1080 -- worth +14% single-stream and +24% at 8
concurrent to them.

So there is room of roughly the same size.  **But check this first:**
GRIMOIRE captures the decode step as a SYCL command graph and replays
it (`build_graph`), which removes per-launch submission cost wholesale.
If replay is live on the B70, launch count is largely moot and fusing
kernels is wasted effort; if it is NOT live, this is the biggest
single lever on the page.  The capability banner says which.  Note that
capture is refused outright for qwen4_exp (see rule 18's neighbours),
so that architecture pays the full launch cost today.

## 3. What is worth copying from the AMD stack, and what is not

Worth copying, in order, ONCE batching exists:

- the small-M decode GEMM with split-K.  Their reason is generic, not
  AMD-specific: at M=20-40 a tuned kernel picks NUM_KSPLIT=1 and leaves
  the grid underfilled.  Rule 5 already gives us the small TILE; the
  split is the part we do not have.
- KV cache sized from the card rather than from a utilisation budget:
  739,544 -> 943,581 tokens, +20.7% concurrency, no compute change.
- dynamic draft width, which is lossless by construction.

NOT worth copying:

- NVFP4 arithmetic.  Its speed is Blackwell tensor cores; Battlemage has
  no FP4 path.  Reading the format (which we now do) is a compatibility
  win, not a speed one.
- their GDN `in_proj` single-GEMM merge.  It won them -2.9%; the
  equivalent here (`GRIMOIRE_FUSE_DN_PROJECTIONS`) measured SLOWER on
  B70 and is off for that reason.  Genuinely architecture-specific.

## 4. Two of their results that are free to take

Both are settled measurements that cost them time and cost us nothing:

- **A drafter must be FP8, not MXFP4.**  MXFP4 RTN dropped acceptance
  2.5 -> 2.21 and AWQ did not rescue it (the per-32 E8M0 block exponent
  already does what per-channel scaling would); FP8 e4m3 per-channel
  holds 2.60-2.80.  Check what format GRIMOIRE quantizes its MTP head
  and DFlash drafter to before measuring acceptance on the Tower.
- **A checkpoint trap.**  `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` will not
  load anywhere as shipped: its `exclude` list names TENSOR names where
  quark matches MODULE names, so the mtp.* layers stay bf16 and the
  loader asserts on a half-width parameter.  Their `fp8_mtp.py` rewrites
  it.  If that checkpoint appears on the Tower, this is why it fails.

## 5. The honest order of work on day one

1. Get preflight green (`tools/preflight_b70.sh`).  Nothing below counts
   until it is.
2. Read the capability banner: is graph replay live?  Is batched prefill
   live?  Those two answers decide which of the items above is worth
   anything.
3. `tools/count_launches.sh` on the real model, for a number to compare
   against.
4. Only then pick a lever.  Every ranking above is a prediction, and
   this project's history is that predictions about which kernel change
   pays do not survive contact with the card (rules 8, 15, and the AMD
   stack's own "fill the GPU before judging a tiling", where an M=2048
   microbench on an idle GPU shipped a 14% regression at the real M).
