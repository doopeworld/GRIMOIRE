Correctness, both models: Paris; llama-benchy coherence PASS; coding 2/2 at each of 4K / 8K / 16K / 32K-token prompts;
4 coding answers at once, two rounds, 8/8.

- Prompts: MXFP4 is faster at every length and user count (+2% to +13%).
- Decode: Swift is faster (+16% to +22% on code, +6% to +23% tg128 for one user up to 16K, +17% to +33% with
  two users). Tokens per update are the same (about 5), and both heads are the same size, so the gap is GRIMOIRE's
  MXFP4 decode / verify kernels against its INT4 ones; the prompt gap runs the other way (INT4 prompt path slower).
- Four users with prompts of 8K and more: the four prompts are prefilled one after another while the first users
  decode, so these decode cells measure that overlap, not the model (spread up to +/- 60). Swift at 16K / 4 users is
  low in both runs (33.8 +/- 0.04) with all 4 slots in VRAM (4.5 GiB KV); not explained yet.

Qwen3.8-27B-FP8, tensor parallel + MTP with the GRIMOIRE-DUAL-QWEN3.8 profile's settings, the same binaries
(`tp-small-bf16-1104`), `GRIMOIRE_TP_SMALL_BF16=0` then `=1`. Logs `ab1104-qwen-tp-bf16-*`.

Each all-reduce waits for about 204 us of queued compute -- a rank's half of one layer's FP8 weights at ~550 GB/s --
so this check pass is weight-read bound; the exchange is about a quarter of it. bf16 partials are now the default on
`tp-small-bf16-1104` (`GRIMOIRE_TP_SMALL_BF16=0` = fp32), the same rounding the prompt path's all-reduce uses.

The same run with v1.10.3's own binaries (stopped after its coding checks, see the handoff): coding 2/2 at 83.8 tok/s,
8/8 concurrent: v1.10.3 works on two cards with gpu1 at Gen3.

## Arc B580, first run

v1.10.3's own G21 binaries, Ornith-1.5-35B-A3B-NVFP4 with tiered experts (`GRIMOIRE_TIERED_MOE=1`), which do not
fit 12 GB: `GRIMOIRE_EXPERT_VRAM_GB=6` puts 90 of 256 experts per layer in VRAM (5.9 GB) and 166 in pinned RAM,
computed on the CPU in decode. Prompt attention runs the XMX kernel on G21 ("joint_matrix flash on XMX -- 16 heads,
2 KV heads, width 256"). Answers correct: Paris; a coherent story; working code.

Decode was 8.9 tok/s, but it was measured beside the v1.10.4 build on 8 cores and with v1.10.3's CPU-expert pool,
which stalls when other processes are busy (fixed in v1.10.4): not a speed result. The comparison against llama.cpp
on the same card runs after the v1.10.4 gate.

v1.10.3's default tiered-expert budget, 16 GB, is larger than the card; `tp-small-bf16-1104` caps it at 60% of the
card (B70 unchanged at 16 GB, B60 14.4 GB, B580 7.2 GB).
