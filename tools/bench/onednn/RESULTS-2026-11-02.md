## Ornith coding failures are the model's

Same four coding prompts, two rounds, together and one at a time, on this image:

| Weights | Pass together | Pass alone | Round 0 = round 1, alone |
|---|---:|---:|---:|
| Safetensors MXFP4 | 4/8 | 6/8 | 4/4 |
| GGUF as MXFP4 | 8/8 | 8/8 | 4/4 |
| GGUF native | 7/8 | 6/8 | 4/4 |
| GGUF native + `GRIMOIRE_MOE_NATIVE_SMALLM=1` | 6/8 | 6/8 | 4/4 |

Earlier the same evening, on the integration binaries, all 8 alone answers were byte-identical with the option off and on, and one prompt
failed in every round in both modes: clean Python that skips the sort. These answers are near a tie, and running together changes which
prompt trips, not how many in any consistent way. That is why grouping is safe to turn on by default, and why this is not a batching defect.

## CPU-expert pool on a busy machine

**Cause.** `CpuExperts::run` waited for every worker to check in, including a worker whose core had gone to another
process. With one other busy process, the caller waited for the last worker 3,225 of 3,347 us per call; the work takes about 120 us.

**Fix, branch `cpu-pool-late-workers-1102`.** The caller works through every item itself. A worker that reaches a job while it is open
helps, and one that does not misses it. Only workers inside are waited for. Which threads helped never changes the arithmetic.

Flash-Next, 64 tokens, the regression's short case. Text is identical to the regression in every row. Seconds:

| Release build | 16.67 | 4.78 | not run |
| One process stuck on a worker's core | 17.32 | 3.77 | not run |
| One process stuck on the decode thread's core | 39.23 | 39.47 | 3.67 |
| One ordinary process | not run | 3.61 | 3.69 |
| Four ordinary processes | not run | 5.20 | 4.98 |

**Versions.** Everything above measured the first version (`2ea7f54`), which cost 6 us of each 85 us call on a quiet machine in the bench
(13 workers retrying a compare-exchange), though not measurably in the engine. The final code (`ec153fa`) enters with one wait-free `fetch_add`: quiet median
old 85.5 / 85.2, final 85.8 / 85.7. It also leaves one card's decode thread free by default; the "free" column set that by environment
variable. **The final code has not run on the GPU yet.**

`tests/test_cpu_expert_pool.cpp`: 1/2/6/14/14 threads with start/stop cycles agree. Thread sanitizer: no reports on the final code.
Control: the first version with relaxed atomics gives 43 race reports, so a clean run means something.
Two-card behavior is unchanged in code (two ranks keep the pin) and not retested.

## Narrow INT4 verify plan: dropped

A first probe reported the narrow split-K plan up to 47% faster for 9-16 row verify. That was wrong. The probe's kernels shared SYCL names with
`libgrimoire_gemm.so` and every column ran the probe's own 128-register image. With their own names, median microseconds at M=16, 54 cases per run, 0 failures:

| Weight | Group | Shipping: 256 registers, current plan | 128, current plan | 128, narrow plan | 256, narrow plan |
|---|---:|---:|---:|---:|---:|
| gate_up 34816 x 5120 | 128 | 197 | 224 | 199 | 188 |
| down 5120 x 17408 | 128 | 112 | 131 | 113 | 132 |
| 10240 x 5120 | 128 | 71 | 85 | 74 | 87 |
| 6144 x 5120 | 128 | 49 | 56 | 51 | 58 |
| head 248320 x 5120 | 128 | 1283 | 1412 | 1257 | 1231 |
| gate_up 34816 x 5120 | 64 | 220 | 337 | 256 | 199 |
| down 5120 x 17408 | 64 | 122 | 155 | 168 | 146 |
| head 248320 x 5120 | 64 | 1418 | 2635 | 1396 | 1357 |

The probe's own copy of the shipping kernel matches the library within 1%, which checks the method. Narrow on 256 registers is 4-10% faster on the
two widest weights and 15-22% slower on the others. No engine change.
