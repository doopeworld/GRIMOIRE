# Gemma-4-31B-it — what it needs, read from the reference not guessed

`google/gemma-4-31B-it`, `Gemma4ForConditionalGeneration`, transformers
5.5.0.dev0. **Not supported today.** This file records what the
architecture actually requires, taken from `ref/gemma4.py` (the real
`modeling_gemma4.py`) and `ref/gemma4_proportional_rope.py`, so the next
session implements rather than guesses — the failure mode `CLAUDE.md`
opens with.

Text tower: 60 layers, hidden 5376, 32 query heads, intermediate 21504,
vocab 262144, tied embeddings, RMS eps 1e-6, sliding window 1024,
`layer_types` = five `sliding_attention` then one `full_attention`,
repeated ten times.

## What GRIMOIRE already has

`layer_types` with sliding/full interleave; per-head q/k RMSNorm; tied
embeddings; sandwich FFN norms (on the Muse path).

## What it does NOT have, and why each one is silent if faked

Nine items. Every one of them loads cleanly and produces fluent text if
implemented wrongly — none of them raises.

### 1. GeGLU
`hidden_activation: "gelu_pytorch_tanh"`. The engine implements exactly
one gated MLP — swiglu, `silu(gate) * up` — in the decode GEMV, the
batched prefill, the MoE path and the speculative verify. There is no
GeGLU kernel anywhere.

Until 2026-09-14 the loader did not even READ `hidden_act`, so this
checkpoint would have loaded and run silu in gelu's place. It now refuses
by name. That refusal is the current behaviour: correct, and not support.

### 2. Per-layer-type attention geometry
`per_layer_config[layer_idx]` gives each layer its own `head_dim` and
`num_key_value_heads`:

| layer type | head_dim | kv heads |
| --- | --- | --- |
| sliding_attention | 256 | 16 |
| full_attention | **512** | **4** |

`Qwen35Config` holds `head_dim`, `n_heads` and `n_kv_heads` as
MODEL-WIDE scalars. They are baked into KV-cache allocation, every
attention launch, scratch sizing and the TP row sharding. This is the
structural item, and the largest.

### 3. `attention_k_eq_v: true` — full layers have NO v_proj
Read `ref/gemma4.py` around the attention forward. On a non-sliding
layer there is no `v_proj` weight at all, and:

```python
value_states = self.v_proj(h).view(shape) if self.v_proj is not None else key_states
key_states   = self.k_norm(key_states)          # rebinds; value keeps the RAW tensor
key_states   = apply_rotary_pos_emb(key_states, cos, sin, unsqueeze_dim=2)
value_states = self.v_norm(value_states)        # scaleless RMSNorm
```

So V is the **pre-norm, pre-RoPE** k_proj output, then a scaleless
RMSNorm; K is the same projection with `k_norm` AND RoPE applied. They
share a projection and diverge immediately after it. Anyone implementing
this from the config alone would almost certainly take V after the norm,
or after RoPE, and the model would still produce fluent text.

`v_norm` is `Gemma4RMSNorm(head_dim, eps, with_scale=False)` — no weight.

### 4. Proportional RoPE on full layers, plain RoPE on sliding ones
`rope_parameters` is keyed BY LAYER TYPE:

| layer type | rope_type | theta | partial_rotary_factor |
| --- | --- | --- | --- |
| sliding_attention | default | 10000.0 | — |
| full_attention | **proportional** | 1000000.0 | 0.25 |

`proportional` is NOT GRIMOIRE's `partial_rope`. See
`ref/gemma4_proportional_rope.py`: the frequency exponent divides by the
FULL `head_dim` (512), not by the rotated width, and the cos/sin table
stays `head_dim/2` wide with zeros past `rope_angles` — so dim `i` pairs
with dim `i + head_dim/2` = `i + 256`. GRIMOIRE rotates `rot =
head_dim*factor` dims and pairs `j` with `j + rot/2` = `j + 64`, with the
exponent over `rot`. Different frequencies AND a different pairing. A new
kernel, not a parameter.

### 5. Attention scale is 1.0
`self.scaling = 1.0` in the reference. GRIMOIRE uses `1/sqrt(head_dim)`
everywhere. Silent, and wrong by 16x at head_dim 256.

### 6. `final_logit_softcapping: 30.0`
`logits = tanh(logits / 30) * 30` before sampling. Not implemented.
There is also an attention-level softcap in the reference; this
checkpoint does not set one, but the code path exists.

### 7. `layer_scalar`, one per layer
`hidden_states *= self.layer_scalar` as the last act of every decoder
layer, after the residual add. Not in `config.json` at all — only the
weight map reveals it. See the weight-map section below.

### 8. Embedding scaling
`Gemma4TextScaledWordEmbedding(..., embed_scale = hidden_size ** 0.5)` —
embeddings are multiplied by sqrt(5376) ≈ 73.32 on lookup. Not
implemented.

### 9. Sandwich FFN norms on the generic path
`pre_feedforward_layernorm` and `post_feedforward_layernorm` exist on
every layer. GRIMOIRE has these, but only wired on the Muse path.

## Not needed for THIS checkpoint
`enable_moe_block: false`, `num_experts: null` — dense, so the MoE path
is not involved. `num_kv_shared_layers: 0` — no cross-layer KV sharing.
`hidden_size_per_layer_input: 0` — the per-layer-input embeddings are
off. The vision and audio towers are out of scope for a text engine;
note that the VISION config also carries `hidden_activation:
"gelu_pytorch_tanh"`, which is why the activation check reads the text
block only and never falls back to the whole file.

## Order to implement

1. GeGLU kernel and its dispatch, plus a loader-driven activation choice.
2. Per-layer-type geometry in `Qwen35Config` and everything sized from it.
   Do this before the rest; items 3 and 4 both depend on knowing a
   layer's own head_dim.
3. The k_eq_v value path, exactly as quoted above.
4. A proportional-RoPE kernel, selected per layer type.
5. Attention scale, logit softcapping, embedding scale.
6. Then MTP / DFlash2, then PP / TP — both of which shard on
   `head_dim` and `n_kv_heads` and so cannot be done before 2.

Pin each step with a config test in the shape of
`tests/test_agnes_config.cpp`, against the REAL `config.json`.

## The weight map, and what it PROVES

`model.safetensors.index.json` is in hand. 32.68 B parameters, 62.5 GB in
two shards. It confirms two readings and adds one feature the config
never mentions.

### It confirms `attention_k_eq_v` empirically
These layers have `q_proj`, `k_proj`, `o_proj`, `q_norm`, `k_norm` and
**no `v_proj` at all**:

    5, 11, 17, 23, 29, 35, 41, 47, 53, 59

Those are exactly the ten `full_attention` positions in `layer_types`.
The 50 sliding layers all carry a `v_proj`. So the reference reading is
not an interpretation: the weights for V do not exist on full layers.

There is also **no `v_norm` tensor anywhere**, which agrees with
`Gemma4RMSNorm(..., with_scale=False)` — that norm has no parameter.

### It adds `layer_scalar` — a feature the config does not mention
Every layer carries `model.language_model.layers.N.layer_scalar`. In the
reference it is the LAST thing a decoder layer does:

```python
hidden_states *= self.layer_scalar     # after the residual add
```

A per-layer scale on the residual stream. Ignore it and the model loads,
runs, and drifts — fluent and wrong. It is a `nn.Buffer` initialised to
ones, so a reader of the CODE alone might dismiss it; it is in the
checkpoint, so it is not ones.

### Tensor names
Prefix is `model.language_model.`, not `model.`:

```
model.language_model.embed_tokens.weight
model.language_model.norm.weight
model.language_model.layers.N.input_layernorm.weight
model.language_model.layers.N.post_attention_layernorm.weight
model.language_model.layers.N.pre_feedforward_layernorm.weight
model.language_model.layers.N.post_feedforward_layernorm.weight
model.language_model.layers.N.layer_scalar
model.language_model.layers.N.self_attn.{q,k,o}_proj.weight
model.language_model.layers.N.self_attn.v_proj.weight   # sliding only
model.language_model.layers.N.self_attn.{q,k}_norm.weight
model.language_model.layers.N.mlp.{gate,up,down}_proj.weight
```

**No `lm_head.weight`** — `tie_word_embeddings: true`, so the output
projection is the embedding table. Everything under
`model.vision_tower.` and `model.embed_vision.` is the image tower and
out of scope for a text engine.

## Speculation: DFlash, not MTP — and the drafter EXISTS

This checkpoint has **no MTP head**: no `mtp.*` tensor in the index, no
`num_nextn_predict_layers` in the config. Unlike Ornith and Qwen3.5,
Gemma-4 ships no in-checkpoint drafter, so `GRIMOIRE_MTP=1` has nothing
to load and speculation must go the DFlash route.

**`z-lab/gemma-4-31B-it-DFlash` is that drafter.** An earlier draft of
this file said no public one was known to exist. That was wrong, and
wrong against evidence already in this repository: `tests/test_dflash_config.cpp`
carries a fixture NAMED after it —

```
// gemma-4-31B-it-DFlash: mixed layer types; sliding layers are causal,
// full-attention layers are not.
```

— pinning exactly that shape through `parse_dflash_config`. So the
drafter-side config resolution is already written and already tested:
mixed `layer_types`, a 1024 window on sliding layers, causal on sliding
and non-causal on full, and the 1e-6 default epsilon.

What that does NOT mean is that DFlash works here. A DFlash drafter
consumes the residual stream tapped at TARGET layers, so it cannot run
until the target does. Everything in this file is the prerequisite.

Once the target loads, the multi-GPU side is already in place: DFlash
runs under TP (drafter replicated) and under PP (last stage hosts it,
taps forwarded) as of 2026-09-13 — see
`HANDOFF-2026-09-13-DFLASH-MULTIGPU.md`. The loader also refuses a
drafter whose `hidden_size` differs from the target's, so the drafter
must declare 5376.

Still needed from the drafter: its `config.json` and weight map, to
confirm the tap layer ids, the mask token, the draft vocabulary and
whether it ships its own `lm_head` / `embed_tokens`. Read the four
`dflash` banner lines on the first load — every value in them is silent
when wrong.

## Effort, honestly

This is a larger addition than Agnes. Agnes was a Qwen3.5-shaped hybrid
plus ONE new feature (`parallel_ffn`) that folded into an existing path.
Gemma-4 needs a new activation kernel, a new RoPE kernel, per-layer-type
geometry through every sizing and sharding decision, an attention path
where V has no weights, and three scalar corrections — eight items, of
which the geometry one touches the KV cache, every attention launch,
scratch sizing and TP sharding.

## Progress log

### 2026-09-14 — items 1, 2, 4, 5 landed; the engine now REFUSES the model

**What is done and gated.**

*Config (item 0).* `model_type` `gemma4` / `gemma4_text` is recognised —
deliberately not a prefix match on `gemma`, since gemma/2/3 are different
architectures this engine does not implement. Every field in the nine
items is parsed, including the layer-type-keyed `rope_parameters` block,
which no other checkpoint here has. Features that are off in this
checkpoint but would be silent if faked — `enable_moe_block`,
`num_kv_shared_layers`, `hidden_size_per_layer_input`,
`use_double_wide_mlp`, an unknown `rope_type` — are refused by name.
`tests/test_gemma4_config.cpp` pins all of it against the REAL
`config.json`, plus bidirectional `k_eq_v` validation (a full layer WITH
a `v_proj` and a sliding layer WITHOUT one are both rejected) and the
required `layer_scalar` and sandwich norms.

*GeGLU (item 1).* `launch_geglu` / `launch_geglu_batched` in `ops.cpp`,
tanh approximation. `bin/test_k2_kernels` checks them against a host
reference AND against swiglu on the same input, so "matches" cannot mean
"both did nothing" (measured separation 7.7e-01).

*Per-layer-type geometry (item 2).* `Qwen35Config::layer_head_dim(i)`,
`layer_kv_heads(i)`, `layer_rope_theta(i)`, `layer_partial_rope(i)`,
`layer_rope_proportional(i)`, `max_head_dim()`, `max_kv_heads()` and
`attn_softmax_scale(hd)`. `LayerDev` resolves all of them ONCE at upload
into `kv_heads`, `head_dim`, `rope_theta`, `partial_rope`,
`rope_proportional`, so no forward path re-derives a layer's shape.

Every per-layer site in `forward()`, `forward_dag()`, the batched
`prefill()` and both MTP paths now reads `LayerDev`, not `cfg`. Every
shared allocation — attention output, q/g split, split-K partials, the
drafter's verify staging, MoVA scratch — is sized from `max_head_dim()` /
`max_kv_heads()`. The prefix cache, which used one model-wide `kv_bytes`
for every layer, is now sized per layer; with two geometries in one model
that single number would have under-allocated half the layers.

For every architecture that exists today the per-layer and model-wide
values are identical, which is what makes `bin/test_model_matrix` and
`bin/test_parallel_e2e` a real regression check on the substitution
rather than a formality.

One pre-existing overrun was closed on the way: the bf16 attention path
packs `q|k|v` back to back into `xperm`, needing
`M*(n_heads + 2*kv_heads)*head_dim` elements, but the buffer was sized
from `M*W` where `W` is the widest SINGLE projection — a bound on each of
the three, not on their sum. It is now sized from the sum, per layer.

*Proportional RoPE (item 4).* `launch_rope_proportional` (decode,
`ops.cpp`) and `launch_qk_norm_rope_proportional_batched` (prefill,
`prefill.cpp`). `bin/test_k2_kernels` checks the decode kernel against
`ref/gemma4_proportional_rope.py`, checks that it is distinguishable from
`partial_rope` (4.05 apart), checks that dims past the rotated band are
left untouched rather than scaled, and checks the batched kernel against
the decode one row by row (0.000e+00 — byte-identical) while still 4.35
from `partial_rope`. Prefill/decode divergence in a rotation is otherwise
completely silent: the KV cache just holds keys rotated one way and
queries the other.

The fused `launch_qk_norm_rope` and `launch_qk_norm_rope_bf16_batched`
only know `partial_rope`, so a proportional-RoPE layer is routed off both
of those paths explicitly rather than being given a different float.

*Attention scale (item 5, partial).* `cfg.attn_softmax_scale(head_dim)`
returns `attn_scale` when set and `1/sqrt(head_dim)` otherwise, so
gemma-4's flat `1.0` reaches every attention launch through one
expression and every other model keeps exactly what it had.

**What the engine does with a gemma-4 checkpoint today: refuses it.**

`Grimoire::unsupported_reason()`, called from `build()` before a byte is
uploaded, refuses gemma-4 by name and refuses any gelu checkpoint by
name. This is deliberate and it is where the check belongs: the LOADER
describes what the file is, the ENGINE decides whether a forward path can
execute it, and the two go out of date independently. Keeping the
capability check in the loader would also have made
`tests/test_gemma4_config.cpp` untestable — it needs the parse to
succeed.

`bin/test_model_matrix` now carries `mini::gemma4()` (6 layers, 2 sliding
: 1 full, two geometries, no `v_proj` on full layers, tied embeddings) in
a "must be refused, not silently run" section. It requires the refusal to
be the ENGINE's sentence (`"no gemma-4 forward path"`), not merely a
message containing "gemma-4" — the loader's own shape refusals say that
too, so matching the word alone would pass on a malformed fixture and
prove nothing. **When the forward path lands, MOVE that fixture into
`archs`; do not just delete the case.**

6. `final_logit_softcapping: 30.0` — `tanh(logits/30)*30`.

8. Embedding scale ×sqrt(5376).
9. The Gemma sandwich residual graph on a non-Muse path. This is the
   structural one left: gemma-4's layer is
   `h = x + post_attention_layernorm(attn(input_layernorm(x)))` then
   `out = h + post_feedforward_layernorm(mlp(pre_feedforward_layernorm(h)))`,
   which is NOT `forward()`'s graph. It IS `forward_muse()`'s graph, but
   `forward_muse` carries Muse-isms (query_prescale, the scaleless embed
   norm, f16 KV caches, NoPE layers) that would have to be made
   conditional. A separate `forward_gemma4()` / `prefill_gemma4()` pair
   is the lower-risk choice and does not put a working, tested Muse path
   at risk.

**10. Sliding-window attention — an item the original nine missed.**
`sliding_window: 1024` applies to 50 of the 60 layers. Nothing in this
engine masks an attention window; every layer attends to the full
history. For prompts under 1024 tokens that is identical, which is
exactly why it would pass a short-prompt smoke test and be wrong on real
input. Either implement the window in the flash kernels or keep the
refusal.

Then MTP/DFlash and PP/TP, both of which shard on `head_dim` and
`n_kv_heads` — the accessors they need now exist, which was the blocker.

**11. head_dim 512 exceeds what the flash kernels can hold — found
2026-09-14, and only the Tower can settle it.**
Every flash kernel in `attention.cpp` and `prefill.cpp` accumulates one
head into a PRIVATE array of `MAX_DPL` floats per lane, with
`dpl = head_dim / SG_SIZE` and `SG_SIZE` 16 — so 256 is the widest head
they can hold. gemma-4's full-attention layers are **512**. A head that
wide writes past the end of a device stack array: a DEVICE_LOST and a
power cycle, not a wrong number.

No supported model had ever exceeded it (Qwen 128, K2 and Muse 256),
which is why it sat there unnoticed. `MAX_DPL` and `MAX_HEAD_DIM` now
live in `src/kernels.hpp` with a `static_assert` at each former
definition site, and `Grimoire::unsupported_reason()` refuses any
checkpoint above the bound by name.

Raising it is not a one-line change: `attention.cpp`'s accumulator loops
run to `MAX_DPL` UNCONDITIONALLY (unlike `prefill.cpp`, which guards each
slot with `if (j < dpl)`), so doubling the constant doubles the
accumulator work for every model, head_dim 128 included. The fix is to
bound those loops by `dpl` as prefill already does, and then measure the
register pressure at dpl 32 on a real B70. Rule 8 applies: no claim about
it from a container.

This is a hard blocker for gemma-4 that cannot be closed here.
