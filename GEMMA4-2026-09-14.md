# Gemma-4-31B-it — what it needs, read from the reference not guessed

`google/gemma-4-31B-it`, `Gemma4ForConditionalGeneration`, transformers
5.5.0.dev0. **Not supported today.** This file records what the
architecture actually requires, taken from `ref/gemma4.py` (the real
`modeling_gemma4.py`) and `ref/gemma4_proportional_rope.py`, so the next
session implements rather than guesses — the failure mode `CLAUDE.md`
opens with.

Text tower: 60 layers, hidden 5376, 32 query heads, intermediate 21504,
vocab 262144, tied embeddings, RMS eps 1e-6, sliding window 1024,
`layer_types` = five `sliding_attention` then one `full_attention`,
repeated ten times.

## What GRIMOIRE already has

`layer_types` with sliding/full interleave; per-head q/k RMSNorm; tied
embeddings; sandwich FFN norms (on the Muse path).

## What it does NOT have, and why each one is silent if faked

Nine items. Every one of them loads cleanly and produces fluent text if
implemented wrongly — none of them raises.

### 1. GeGLU
`hidden_activation: "gelu_pytorch_tanh"`. The engine implements exactly
one gated MLP — swiglu, `silu(gate) * up` — in the decode GEMV, the
batched prefill, the MoE path and the speculative verify. There is no
GeGLU kernel anywhere.

Until 2026-09-14 the loader did not even READ `hidden_act`, so this
checkpoint would have loaded and run silu in gelu's place. It now refuses
by name. That refusal is the current behaviour: correct, and not support.

### 2. Per-layer-type attention geometry
`per_layer_config[layer_idx]` gives each layer its own `head_dim` and
`num_key_value_heads`:

| layer type | head_dim | kv heads |
| --- | --- | --- |
| sliding_attention | 256 | 16 |
| full_attention | **512** | **4** |

`Qwen35Config` holds `head_dim`, `n_heads` and `n_kv_heads` as
MODEL-WIDE scalars. They are baked into KV-cache allocation, every
attention launch, scratch sizing and the TP row sharding. This is the
structural item, and the largest.

### 3. `attention_k_eq_v: true` — full layers have NO v_proj
Read `ref/gemma4.py` around the attention forward. On a non-sliding
layer there is no `v_proj` weight at all, and:

```python
value_states = self.v_proj(h).view(shape) if self.v_proj is not None else key_states
key_states   = self.k_norm(key_states)          # rebinds; value keeps the RAW tensor
key_states   = apply_rotary_pos_emb(key_states, cos, sin, unsqueeze_dim=2)
value_states = self.v_norm(value_states)        # scaleless RMSNorm
```

So V is the **pre-norm, pre-RoPE** k_proj output, then a scaleless
RMSNorm; K is the same projection with `k_norm` AND RoPE applied. They
share a projection and diverge immediately after it. Anyone implementing
this from the config alone would almost certainly take V after the norm,
or after RoPE, and the model would still produce fluent text.

`v_norm` is `Gemma4RMSNorm(head_dim, eps, with_scale=False)` — no weight.

### 4. Proportional RoPE on full layers, plain RoPE on sliding ones
`rope_parameters` is keyed BY LAYER TYPE:

| layer type | rope_type | theta | partial_rotary_factor |
| --- | --- | --- | --- |
| sliding_attention | default | 10000.0 | — |
| full_attention | **proportional** | 1000000.0 | 0.25 |

`proportional` is NOT GRIMOIRE's `partial_rope`. See
`ref/gemma4_proportional_rope.py`: the frequency exponent divides by the
FULL `head_dim` (512), not by the rotated width, and the cos/sin table
stays `head_dim/2` wide with zeros past `rope_angles` — so dim `i` pairs
with dim `i + head_dim/2` = `i + 256`. GRIMOIRE rotates `rot =
head_dim*factor` dims and pairs `j` with `j + rot/2` = `j + 64`, with the
exponent over `rot`. Different frequencies AND a different pairing. A new
kernel, not a parameter.

### 5. Attention scale is 1.0
`self.scaling = 1.0` in the reference. GRIMOIRE uses `1/sqrt(head_dim)`
everywhere. Silent, and wrong by 16x at head_dim 256.

### 6. `final_logit_softcapping: 30.0`
`logits = tanh(logits / 30) * 30` before sampling. Not implemented.
There is also an attention-level softcap in the reference; this
checkpoint does not set one, but the code path exists.

### 7. `layer_scalar`, one per layer
`hidden_states *= self.layer_scalar` as the last act of every decoder
layer, after the residual add. Not in `config.json` at all — only the
weight map reveals it. See the weight-map section below.

### 8. Embedding scaling
`Gemma4TextScaledWordEmbedding(..., embed_scale = hidden_size ** 0.5)` —
embeddings are multiplied by sqrt(5376) ≈ 73.32 on lookup. Not
implemented.

### 9. Sandwich FFN norms on the generic path
`pre_feedforward_layernorm` and `post_feedforward_layernorm` exist on
every layer. GRIMOIRE has these, but only wired on the Muse path.

## Not needed for THIS checkpoint
`enable_moe_block: false`, `num_experts: null` — dense, so the MoE path
is not involved. `num_kv_shared_layers: 0` — no cross-layer KV sharing.
`hidden_size_per_layer_input: 0` — the per-layer-input embeddings are
off. The vision and audio towers are out of scope for a text engine;
note that the VISION config also carries `hidden_activation:
"gelu_pytorch_tanh"`, which is why the activation check reads the text
block only and never falls back to the whole file.

## Order to implement

1. GeGLU kernel and its dispatch, plus a loader-driven activation choice.
2. Per-layer-type geometry in `Qwen35Config` and everything sized from it.
   Do this before the rest; items 3 and 4 both depend on knowing a
   layer's own head_dim.
3. The k_eq_v value path, exactly as quoted above.
4. A proportional-RoPE kernel, selected per layer type.
5. Attention scale, logit softcapping, embedding scale.
6. Then MTP / DFlash2, then PP / TP — both of which shard on
   `head_dim` and `n_kv_heads` and so cannot be done before 2.

Pin each step with a config test in the shape of
`tests/test_agnes_config.cpp`, against the REAL `config.json`.

## The weight map, and what it PROVES

`model.safetensors.index.json` is in hand. 32.68 B parameters, 62.5 GB in
two shards. It confirms two readings and adds one feature the config
never mentions.

### It confirms `attention_k_eq_v` empirically
These layers have `q_proj`, `k_proj`, `o_proj`, `q_norm`, `k_norm` and
**no `v_proj` at all**:

    5, 11, 17, 23, 29, 35, 41, 47, 53, 59

Those are exactly the ten `full_attention` positions in `layer_types`.
The 50 sliding layers all carry a `v_proj`. So the reference reading is
not an interpretation: the weights for V do not exist on full layers.

There is also **no `v_norm` tensor anywhere**, which agrees with
`Gemma4RMSNorm(..., with_scale=False)` — that norm has no parameter.

### It adds `layer_scalar` — a feature the config does not mention
Every layer carries `model.language_model.layers.N.layer_scalar`. In the
reference it is the LAST thing a decoder layer does:

```python
hidden_states *= self.layer_scalar     # after the residual add
```

A per-layer scale on the residual stream. Ignore it and the model loads,
runs, and drifts — fluent and wrong. It is a `nn.Buffer` initialised to
ones, so a reader of the CODE alone might dismiss it; it is in the
checkpoint, so it is not ones.

### Tensor names
Prefix is `model.language_model.`, not `model.`:

```
model.language_model.embed_tokens.weight
model.language_model.norm.weight
model.language_model.layers.N.input_layernorm.weight
model.language_model.layers.N.post_attention_layernorm.weight
model.language_model.layers.N.pre_feedforward_layernorm.weight
model.language_model.layers.N.post_feedforward_layernorm.weight
model.language_model.layers.N.layer_scalar
model.language_model.layers.N.self_attn.{q,k,o}_proj.weight
model.language_model.layers.N.self_attn.v_proj.weight   # sliding only
model.language_model.layers.N.self_attn.{q,k}_norm.weight
model.language_model.layers.N.mlp.{gate,up,down}_proj.weight
```

**No `lm_head.weight`** — `tie_word_embeddings: true`, so the output
projection is the embedding table. Everything under
`model.vision_tower.` and `model.embed_vision.` is the image tower and
out of scope for a text engine.

## No speculation is possible with this checkpoint alone

The request was "mtp/dflash2 as usual". This checkpoint has **no MTP
head** — there is no `mtp.*` tensor in the index, and no
`num_nextn_predict_layers` in the config. Unlike Ornith and Qwen3.5,
Gemma-4 ships no in-checkpoint drafter.

So speculation here needs a SEPARATE drafter model, the DFlash route, and
no public gemma-4 DFlash drafter is known to exist. The engine work is
the same either way — a drafter is loaded from its own directory — but
until such a checkpoint exists there is nothing to point it at. PP and TP
do not depend on this and apply normally once the geometry work below is
done.

## Effort, honestly

This is a larger addition than Agnes. Agnes was a Qwen3.5-shaped hybrid
plus ONE new feature (`parallel_ffn`) that folded into an existing path.
Gemma-4 needs a new activation kernel, a new RoPE kernel, per-layer-type
geometry through every sizing and sharding decision, an attention path
where V has no weights, and three scalar corrections — eight items, of
which the geometry one touches the KV cache, every attention launch,
scratch sizing and TP sharding.
